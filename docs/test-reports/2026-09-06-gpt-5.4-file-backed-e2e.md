- 日期：2026-09-06（UTC+8）
- 基线提交：`ec788ba9fc3aeb2528e121de9cece83f92f62346` 加当前工作区改动
- Go：`go1.25.13 linux/amd64`
- 上游协议：OpenAI Responses
- 上游模型：`gpt-5.4`
- Provider：从本机 `~/.codex` 读取；URL、密钥和物理部署名均未写入 fixture、源码或日志

## 结论

当前回归集包含 **63 个独立 request JSON 文件**，对应 **62 个逻辑场景、63 次真实 HTTP 请求**。最终一次完整 provider 回归 **63/63 通过**，耗时 **90.219 秒**。

所有 request 都从 Chat、Responses、Anthropic Messages 或 Gemini GenerateContent 的客户端协议形态进入公开 `Adapter`，再转换为 Responses 请求发送到 provider。默认测试还会把全部 63 个 fixture 发送到本地 Responses mock，并逐项验证转换后的语义，而不只验证 JSON 可解析。

本轮 live 测试发现并修复了一处真实兼容缺陷：Chat、Messages 和 Gemini 的历史 assistant/model 文本原先被编码成 Responses `input_text`，该 provider 对此返回 HTTP 400；改为 `output_text` 后，四入口多轮矩阵 8/8 通过。三条转换路径均有确定性回归锁定 `user → assistant → user` 对应 `input_text → output_text → input_text`。

提交前边界审计还确认：Chat assistant 历史上的 `prompt_cache_breakpoint` 不能附着到 Responses `output_text`。该组合现返回精确路径的 `ErrUnsupported`，不会静默删除字段或发送非法请求；user 输入上的 breakpoint 仍保留并通过回归。

| 分组 | 能力 | 逻辑场景 | request 文件 / HTTP |
|---|---|---:|---:|
| core | 文本、函数调用、函数结果回灌、JSON Schema；四入口 × 流/非流 | 32 | 32 |
| extended | 多轮对话 8、复杂嵌套参数 4、并行工具结果 4、metadata/service tier 2 | 18 | 18 |
| tools | custom call 3、custom output 3、web search 3、server tool search 2、client tool search 两轮 | 12 | 13 |
| **合计** |  | **62** | **63** |

模式分布为 24 个 stream、39 个 non-stream。每个请求文件都登记在 `testdata/e2e/responses/catalog.json`；除 client tool-search 第二轮需要注入第一轮返回的 call 与 call ID 外，fixture 均可直接使用。第二轮的两个动态值也保留在一个完整 JSON 请求中，以受限的类型化占位符表示。

## 三类工具结论

### `custom_tool_call`

- Responses 原生非流、原生流以及 Chat→Responses 非流调用均通过。
- Responses 原生非流、原生流以及 Chat→Responses 非流的 `custom_tool_call_output` continuation 均通过。
- 流式用例校验 item added/done、custom input delta/done 和最终输入一致性；Chat 用例校验不会被错误降级成普通 function call。

### `web_search`

- Responses 原生非流、原生流以及 Chat→Responses 非流均通过。
- 请求覆盖 `search_context_size` 和 approximate user location；响应覆盖 search lifecycle、正文顺序和 URL citation。
- Chat 只能保留最终正文与引用，不能表达完整 hosted-search 生命周期，因此保留显式 loss diagnostic。

### `tool_search`

`tool_search` 是 Responses 原生的延迟工具发现能力，不等同于普通 function call：

- `execution:"server"` 是 server-side tool search。provider 负责搜索 deferred tools，响应依次包含 `tool_search_call`、`tool_search_output`，随后模型再发普通 `function_call`。
- `execution:"client"` 不是 server tool call。第一轮模型返回带 `call_id` 的 `tool_search_call`；调用方执行搜索，并在第二轮提交相同 call ID 的 `tool_search_output` 与 `additional_tools`，模型随后调用发现到的函数。
- 这三类 item 没有 Chat、Messages 或 Gemini 的等价表达，跨协议继续 fail closed。

本 provider 对“仅声明一个 client tool_search”时的 `tool_choice:"required"` 和 `tool_choice:{"type":"tool_search"}` 均返回 HTTP 400，因此 client 首轮 fixture 没有写这两个强制选项。用例通过明确提示词触发搜索，并严格断言只能取得一个可关联的 `tool_search_call`；这是当前 provider 的已知行为边界。

## Fixture 维护与本地门禁

普通测试会执行以下检查：

- 精确锁定全部 63 个 ID 及其 protocol、stream、assertion、dynamic 元数据，防止用同数量的其他用例替换既定矩阵；
- request 路径与 ID 一致、无重复、无 orphan、无缺失文件，且每个文件是完整 JSON object；
- 只允许 client tool-search 第二轮使用两个指定 placeholder，并要求各出现一次；拒绝任何残留的 `{{...}}`、`}}` 或 `$live_fixture`；
- 对 catalog、原始 request 和渲染后 request 递归扫描 credential/provider 字段和值；
- 将每个请求通过公开 Adapter 转成 Responses，并按 assertion 校验文本输入、assistant-history content type、JSON Schema、函数或 custom 工具、call/output 关联、web location、tool-search execution/correlation、metadata 和 service tier；
- 用目标客户端协议解析 mock 的非流响应，或解码并重建流式终态响应。

真实测试另检查 HTTP、路由元数据、模型别名恢复、token usage、终止状态、允许的 diagnostics，以及相应内容或工具生命周期。

## 已知边界

- 多模态文件/图片、故意触发的鉴权失败、限流、超大响应和畸形 SSE 不发送到真实 provider；这些风险由本地确定性测试和 fuzz 覆盖。
- custom/web/tool-search 只测试协议可表达的入口组合；不把 Responses-native 生命周期伪造到不兼容协议。
- client tool-search 首轮是否选择搜索仍受模型/provider 行为影响；当前使用强提示和严格输出断言，因为该 provider 不接受上述两个强制 `tool_choice` 形态。
- live 结果是 2026-09-06 的 provider 快照，后续模型路由或 provider schema 变化仍需重新执行完整矩阵。
