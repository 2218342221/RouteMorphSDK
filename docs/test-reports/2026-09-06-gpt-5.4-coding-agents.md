# RouteMorphSDK coding agents → Responses / gpt-5.4 回归报告

- 日期：2026-09-06（UTC+8）
- 基线提交：`76f9f494c8f520b2123768952d7d00fc941f3831` 加当前工作区改动
- 上游协议 / 模型：OpenAI Responses / `gpt-5.4`
- Go / Node：`go1.25.13 linux/amd64` / `v24.4.1`
- 主机：Linux `5.15.120.bsk.3-amd64` x86_64
- 客户端：Claude Code `2.1.210`、Gemini CLI `0.22.5`、Codex CLI `0.149.1`
- Provider 配置：运行时从本机 `~/.codex` 读取；URL、SK 和路由 header
  的值均未写入源码、fixture、测试输出或本报告

## 结论

本轮为 SDK 增加了显式、默认关闭的 coding-agent compatibility profile，
并在同一份最终协议实现上完成两层验证：

1. 三个已安装的真实 CLI 共 **9/9 场景通过**，总耗时 **66.08 秒**；
   纯文本、成功读文件、缺失文件错误各一例，实际经过 15 次本地 gateway
   请求和真实 `gpt-5.4` provider 调用。
2. 原有 any → Responses provider 矩阵 **62/62 逻辑场景、63/63 HTTP
   请求通过**，总耗时 **84.377 秒**。
3. `make check` 全通过，覆盖 fmt、vet、普通测试、race、integration 编译、
   build 和 provider SDK 示例模块。仓库当前有 483 个 `Test*` 函数，较基线
   新增 33 个，另有 3 个 fuzz 目标和 2 个 benchmark。

因此，可以确认上述三个客户端版本的核心 agent 闭环——模型文本、工具调用、
工具结果回灌和工具失败回灌——能够通过 RouteMorphSDK 使用该 Responses
provider 的 `gpt-5.4`。这不是对客户端所有命令、插件、MCP、hosted tool 或未来
版本的无条件保证；边界见下文。

## 实现范围

公开入口新增 `WithCodingAgentCompatibility()`。严格、fail-closed 行为仍是默认值，
该 option 也不会打开 SDK 内部更宽泛的 `AllowDocumentedLoss`：

- Claude Code → Responses：接受当前 `adaptive` / `display:"omitted"` thinking
  形态和 no-op `clear_thinking_20251015`，递归剥离 exact ephemeral cache marker，
  对过长 `metadata.user_id` 做稳定、分域 SHA-256 假名化，并保留 tool error
  正文；每个不能等价表达的字段都产生 diagnostic。
- Responses → Claude Code：reasoning summary/raw/encrypted state 不伪装成普通正文，
  而是按兼容策略省略并产生 diagnostic；流式 reasoning item 仍校验 item id、类型
  和生命周期。
- Gemini CLI → Responses：允许省略 `topK`、`thinkingBudget`、
  `includeThoughts`，只识别 exact `skip_thought_signature_validator` sentinel，
  并把 function-response error object 序列化进 tool output；近似 sentinel 和真实
  provider signature 仍拒绝。
- Responses → Gemini CLI：summary 可作为 unsigned thought 输出，opaque encrypted
  reasoning 被省略并报告 diagnostic；拒绝把真实签名或 refusal 语义伪造成普通文本。
- Codex → Responses：保持原生 request 透传（除显式 model override），并加强 SSE
  生命周期校验，包括 `created` identity、reasoning raw content、terminal enrichment、
  failed/cancelled terminal 和 terminal snapshot reconciliation。
- minimal gateway 支持 `CODING_AGENT_COMPATIBILITY=true`，并在流结束后只记录
  diagnostic 的 severity、code 和结构化 path，不记录可能含 payload 的 message。

测试不会仅因“出现过某个工具结果”而通过。工具场景必须同时满足：工具名正确、
arguments 指向指定文件、result 与该 call ID 相同、成功内容或失败语义正确、最终输出
精确匹配。文本场景反向断言不存在任何 call/result 事实。

观察到的转换信号也与设计一致：Claude 请求触发 thinking/cache 等显式 diagnostics，
Claude tool-error 触发 `tool_result_error_state_not_representable`；Gemini 请求触发
thinking-budget / thought-signature diagnostics，tool-error 触发
`gemini_function_error_state_not_representable`；Codex 原生路径为零 conversion
diagnostic。gateway 捕获的原始请求体不写入持久文件；CLI 临时 state、fixture 和
Codex last-message 只写入 `t.TempDir` 并由测试自动清理。测试日志只保留路径、
diagnostic code、字节数和截断 SHA-256 fingerprint。

## 确定性回归集

新增和扩展的本地回归主要锁定：

- public option 能完整穿过 Adapter，同时不能放开无关的 Responses → Chat cache loss；
- Claude Code 首轮请求、当前 adaptive thinking、嵌套 tool-result cache marker、tool
  error、长 user id、reasoning 非流/流转换，以及未知/wrong reasoning item 的负向用例；
- Gemini CLI generation config、exact synthetic signature、tool continuation/error、
  Responses reasoning summary，以及近似/真实 signature 的负向用例；
- Codex 0.149.1 的代表性 native Responses request 和完整 SSE lifecycle 保真；
- terminal snapshot 只允许受控 enrichment：拒绝既有 scalar 改写、已知字段后加、
  nested unknown enrichment、跨 variant 字段和 identity 漂移，仅允许已审计 extension、
  message phase、output-text logprobs 与 reasoning ciphertext refresh；
- `response.failed` / `response.cancelled` 的必填字段、错误对象和 terminal 行为；
  cancelled 在原生 Responses 中保真透传，在 Chat/Messages/Gemini 跨协议 stream 中
  明确归类为 `ErrUpstreamResponse`，而不是未知能力 `ErrUnsupported`；
- live harness 的超时进程组终止、handler 完成同步、异常断流分类、临时客户端配置
  隔离，以及不含凭据的证据输出。

原有 63 个文件化 request fixture 继续覆盖 Chat、Responses、Messages、Gemini 四入口
的流/非流文本、函数调用/结果、结构化输出、多轮、复杂/并行工具、metadata、service
tier、custom tool、web search 和 tool search。它们既通过本地 mock 做确定性转换验证，
也在本轮重新全部发送到真实 provider。

## 隔离和保密边界

真实 CLI 测试通过 loopback gateway 给客户端注入 placeholder credential，真实 URL、
SK 和可选路由 header 只存在于 Go 测试进程。Linux `bwrap` 用每 case 临时目录覆盖
客户端看到的 canonical home，并只开放临时 state/workspace 写入；Gemini 的 extension、
MCP、context、hook、telemetry 和非 `read_file` core tool 被禁用。

该机制是配置与写隔离，不是完整安全沙箱：home 外的 host filesystem 仍只读可见，
客户端仍有网络访问。对不完全信任的客户端，应在一次性主机或容器中运行 billable
测试。

## 已知边界

- compatibility profile 有意包含有诊断的近似；调用方必须在 stream EOF 后读取并
  处理 `Response.Meta.Diagnostics()`，不能把“HTTP 成功”解释为完全无损。
- cache TTL/cost 细分、provider-issued reasoning/signature replay state、hosted tools、
  `countTokens`、embedding、MCP 和客户端插件不在本轮三类 CLI 场景内。
- 跨协议不会伪造 opaque reasoning state；Claude/Gemini 的可见 reasoning 处理仍受
  `docs/compatibility.md` 与 `docs/unsupported.md` 中的精确边界约束。
- 当前结论绑定上表三个客户端版本和 2026-09-06 的 provider 行为。升级客户端、
  provider schema 或模型路由后应重新执行两套 live 回归。
- malformed payload、非 2xx/error envelope、限流、取消、超限和畸形 SSE 主要由本地
  确定性/负向/fuzz 测试覆盖，不故意消耗真实 provider 配额重复制造。

## 复跑

凭据只通过环境变量注入，不应出现在 shell 参数、fixture、报告或提交中：

```bash
export ROUTEMORPH_LIVE_BASE_URL='https://provider.example/v1'
export ROUTEMORPH_LIVE_API_KEY='...'
export ROUTEMORPH_LIVE_MODEL='gpt-5.4'
export ROUTEMORPH_LIVE_X_SOURCE=''

make test-live-coding-agents
make test-live-responses
GOWORK=off make check
```

前两个 target 分别要求 `ROUTEMORPH_LIVE_CLI=1` 和
`ROUTEMORPH_LIVE_RESPONSES=1` 的内部 guard；Makefile 会设置 guard，并在缺少 URL/SK
时提前失败。真实 CLI target 还会在缺少任一客户端或 Linux `bwrap` 时失败，不会静默
skip。
