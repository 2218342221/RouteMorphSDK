最终完整复跑结果：**通过，37/37 场景、38/38 次 HTTP，耗时 59.776 秒**。

### `custom_tool_call`

- Native Responses 非流式要求唯一 `custom_tool_call`，并检查 `id`、`call_id`、`name`、原始字符串 `input` 和终态 `status:"completed"`。
- Native Responses 流式检查 `output_item.added` 的 `in_progress`、一个或多个 `response.custom_tool_call_input.delta`、对应 `.done`、`output_item.done` 的 `completed`，并要求 delta 拼接结果与终态 input 一致。
- Chat→Responses 仅测试受支持的非流式公共子集；返回必须仍是 Chat `type:"custom"`，不能伪装成普通 function call。`custom_tool_call_output` 的历史回灌和错误形态由本地确定性测试覆盖，本次 10 次 live 调用不包含 custom-output continuation。

### `web_search`

- Native Responses 非流式要求至少一个完成的 `web_search_call`，action 为 `search` 且含 query/queries；随后 assistant message 必须有非空正文和完整 URL citation。
- Native Responses 流式要求 `output_item.added → in_progress → searching → completed → output_item.done`，之后才进入 message 文本/引用生命周期；Responses 流不使用 `[DONE]`。
- Chat→Responses 非流式 live case 要求保留最终正文和 URL citation，且不得伪造普通 tool call。Chat 无法表达 Responses 的 hosted-search 生命周期；对应的本地确定性回归精确要求一次 `responses_web_search_call_not_representable` 诊断，live harness 只允许该诊断而不依赖 provider 必然产生固定数量的 search lifecycle item。

### `tool_search`

- Server 模式由 provider 执行发现。本回归场景要求输出顺序为 `tool_search_call → tool_search_output → function_call`，`arguments` 按任意 JSON 值处理，返回的函数定义必须保留 `defer_loading:true`。流式没有专属 tool-search delta，只检查通用 `response.output_item.added/done`、连续 sequence、item 身份和终态对账。
- 兼容 provider 的 server `tool_search_call`/`tool_search_output` 可能省略 `call_id`、`execution`，也可能返回 null。SDK 不补造这些字段；非 null 值仍必须是合法非空 ID和 `server|client` 枚举，双方都给出 ID 时必须一致。
- Client 模式第一轮必须返回可关联的 `tool_search_call.call_id`。第二轮原样回放该 call，并用相同 ID 提交 `tool_search_output`，同时通过 `additional_tools` 提供发现到的 deferred function；最终必须得到目标普通 `function_call`。这一个 subtest 因两轮交互计为两次真实 HTTP。
- `tool_search_call`、`tool_search_output` 和 `additional_tools` 没有 Chat、Messages 或 Gemini 的等价语义，跨协议继续返回 `ErrUnsupported`，不会降级成普通函数调用。

## 发现和修复

### 1. Responses 流式 service tier 状态迁移

真实事件在创建阶段返回 `service_tier:"auto"`，在完成事件返回 `"default"`。旧实现将其误判为流内字段突变，Chat 流在已经输出文本后以 `stream_conversion_error` 结束。

修复后允许 `auto` 单向解析为终态 tier；相同 tier 保持不变，其他具体 tier 之间的变化仍作为无效上游响应 fail-closed，Responses 独有的 `ultrafast` 仍不能输出成 Chat tier。

### 2. 默认 service tier 到 Messages/Gemini

Responses provider 即使客户端未选择 tier，也会在响应中返回 `auto` 或 `default`。Messages 和 Gemini 没有对应响应字段，旧实现会在默认严格策略下拒绝整个有效响应。

修复后仅对 provider 选择的 `auto/default` 省略该字段并产生一次 `responses_service_tier_not_representable` 警告。`priority` 等显式非默认 tier 仍返回 `ErrUnsupported`，未知 tier 返回 `ErrUpstreamResponse`。

### 3. 函数参数完成事件省略 name

真实 Responses 流的 `response.function_call_arguments.done` 不一定重复携带 `name`；函数身份已由同一 item 的 `output_item.added/done` 提供。旧验证器要求 `name`，导致工具调用流失败。

修复后允许该事件省略 `name`，存在时仍要求非空；流生命周期仍必须引用已知的 function-call item，因此没有放松 item 身份和顺序校验。

### 4. `custom_tool_call` 返回 status

Provider 的完整 custom-call item 返回 `status:"completed"`，流式 added item 为 `in_progress`，done 和终态 item 为 `completed`。旧实现把 custom item 上的任意 status 都当成 schema 外字段，导致合法 native 流失败。

修复后在输出和流事件边界接受 `in_progress/completed/incomplete` 的合法生命周期，并继续拒绝未知状态、错误类型和缺少 `call_id`、`name` 或字符串 `input` 的完整 item。Chat 转换仍输出 `type:"custom"`，不会把它冒充为 function call。

### 5. Server `tool_search` 省略 correlation/execution

Provider 的 server discovery 输出可在 `tool_search_call` 和 `tool_search_output` 中省略 `call_id`、`execution`，或将其设为 null；但 `id`、`status`、call 的 `arguments` 和 output 的 `tools` 仍然存在。旧完整 item 校验器把前两项一律当成必填，导致 native Responses 流在 `output_item.done` 被拒绝。

修复后只把这两个字段作为 provider-compatible optional 字段：缺失/null 原样保留，不推断也不补造；非 null `call_id` 必须非空，`execution` 只能为 `server|client`，显式 client execution 仍必须带 `call_id`。流式 item 的 added/done 身份和终态 JSON 对账、tool 定义深校验及跨协议 fail-closed 均保持不变。

## 回归测试集

Opt-in live suite 分为 `live_responses_integration_test.go` 的 28-call 核心矩阵和 `live_responses_tools_integration_test.go` 的 10-call 工具矩阵。二者均通过 `integration` build tag 和 `ROUTEMORPH_LIVE_RESPONSES=1` 双重保护，默认测试和 CI 不会产生计费调用。

Make 入口固定如下：

- `make test-live-responses-core`：四个核心 matrix，28 个场景、28 次 HTTP；
- `make test-live-responses-tools`：三个高级工具顶层测试，9 个场景、10 次 HTTP；
- `make test-live-responses`：运行当前所有 `TestLiveResponsesProvider*`，合计 37 个场景、38 次 HTTP。

Live harness 只接受无 userinfo/query/fragment 的 HTTPS 端点，首个失败即停止；失败信息仅保留状态、类型以及响应长度/哈希，不打印原始 provider payload。默认 `make check` 会编译和 vet integration-tag 代码，但不会选择任何 live test。

确定性回归新增或补强：

- 四入口 × 流/非流的真实 service-tier 事件夹具；
- 四入口的函数调用结果回灌，包括各协议的调用 ID 关联；
- `auto → default`、具体 tier 非法变化、`ultrafast`、未知 tier；
- Messages/Gemini 的默认 tier 单次诊断、非默认 tier 拒绝和未知 tier 校验；
- `function_call_arguments.done` 有/无 `name` 及空 `name`；
- 完整 function-call item 生命周期；
- provider-shaped `custom_tool_call.status`、custom input delta/done 以及 custom/function 类型隔离；
- `web_search_call` action 的 query/queries、URL citation 保留、progress 顺序和 Chat lifecycle-loss 单次诊断；
- server tool-search 缺失/null `call_id`、`execution` 的 native 接受，存在值的严格校验，以及显式 client execution 的 ID 约束；
- `tool_search_call`/`tool_search_output`/`additional_tools` 的 item union、deferred tool 定义、stream added/done/terminal 对账，以及所有非 Responses 目标的 `ErrUnsupported`；
- 官方 SDK 注入：OpenAI Chat、OpenAI Responses、Anthropic Messages、Gemini 的非流式和成功流式路径，以及凭据隔离和模型恢复。

本次文档更新时仓库共有 439 个 `Test*` 函数、3 个 fuzz 目标和 2 个 benchmark。真实 provider 异常、限流、取消、畸形 SSE 和大小限制不会在 live suite 中主动触发，继续由本地确定性与 fuzz 测试覆盖。

## 已知边界

- 多模态输入没有向真实 provider 发送；相关转换由现有本地 fixture 覆盖。
- 没有为报告故意制造鉴权失败、限流或服务端错误，避免无必要流量和告警；错误信封与失败流由确定性测试覆盖。
- 高级工具矩阵不是四协议全覆盖：8 次调用为 Responses-native，2 次为 Chat→Responses 非流式。custom 的 Chat 流、custom output continuation、client tool-search 流、Messages/Gemini 高级工具均未发 live 请求。
- Chat↔Responses 只共享非流式 custom 和 web-search 请求子集；Chat 对 web search 只能保留最终正文/引用。`tool_search` 和 `additional_tools` 仅支持 Responses-native，跨协议不会偷偷改写为普通函数工具。
- reasoning 探测中，简单请求可能不产生 reasoning item；较难请求可能返回 summary 和 opaque `encrypted_content`，也可能因 token 上限以 `incomplete/max_output_tokens` 结束。opaque reasoning 不能可靠映射到其他协议，跨协议继续 fail-closed，不计入本次公共子集的 28 个成功用例。
- live 结果依赖 provider 当时的路由和模型行为；本地回归固定了本次观察到的协议形态，后续仍建议按发布节奏复跑 live suite。
